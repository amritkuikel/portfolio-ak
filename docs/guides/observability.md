# Observability: logs, Sentry, PostHog and feature flags

All optional except the logs. Without their variables, Sentry and PostHog are off: nothing is initialised or downloaded, no consent banner, no network calls. Example: `/dev/examples/analytics`.

## Logs

- **One request id per request** (`src/server/http/request-scope.ts`, 0123): generated by the server entry, returned as the `x-request-id` header, and attached to every log line, every server Sentry event and the `AppError` the user sees (the error page shows it as "Reference"). A support report or a response header leads to the log lines and the Sentry event.
- **One JSON line per server-function call** (`src/middleware/logging.ts`): function name, method, request id, duration and outcome.
- **Other server logs** go through `log(level, msg, fields)` (`src/server/log.ts`), which writes the same JSON shape with the request id. Don't call `console.*` in server code.
- **Levels:** expected refusals (4xx `AppError`) log as `warn`, failures as `error`.
- **Unexpected errors** log once, with their stack, in `normalizeServerError` (`src/middleware/errors.ts`).

## Sentry (`VITE_SENTRY_DSN`)

- **Browser** (`src/lib/observability/sentry-client.ts`) and **server** (`src/instrument.server.ts`, imported first by `src/server.ts`): errors and performance traces, including router navigations.
- **The browser SDK loads after the entry chunk** (0152): `src/client.tsx` starts loading it in parallel with hydration, and errors before it's ready are buffered and sent once it is. In code that also runs in the browser, call `captureException` / `setSentryUser` from `sentry-client.ts`, never import `@sentry/tanstackstart-react` statically (one static import puts the whole SDK back in every page's JavaScript; the bundle budget catches it). Server-only code imports it inside `.server()` or a server module.
- **Traces:** 10% in production. None in development unless `VITE_SENTRY_DEV_TRACING=true` (tracing every dev request slows `pnpm dev`).
- **What's reported:** unexpected server-function errors, once, with the original stack. Every server event is tagged `requestId` (`beforeSend` in `src/instrument.server.ts`). Expected `AppError`s (below 500) aren't reported, and the browser doesn't log them either (`onCaughtError` in `src/client.tsx`).
- **Privacy:** only the user id is attached; the IP address is stripped.
- **Source maps** upload during `pnpm build` when `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` are all set.
- **CSP:** the ingest host is added to `connect-src` only when a DSN is configured.
- **CSP violations** reported by browsers arrive as warnings titled `CSP violation: <directive> blocked <resource>`, one issue per directive and resource, with the page path in the extras (0139). The log line is `csp violation`.

## PostHog (`VITE_POSTHOG_KEY`, optional `VITE_POSTHOG_HOST`)

- **Opt-in:** a consent banner stores the choice in a cookie (`analyticsConsent` preference), rendered on the server so nothing shifts. The footer link changes it later.
- **Before consent:** `posthog-js` isn't downloaded, `track()` is a no-op, and the server sends no events.
- **After consent:** pageviews on navigation, `identify` on login and `reset` on logout, plus feature events: `test_crud_created`, `test_crud_updated` and `test_crud_deleted` (server) and `test_crud_viewed` (browser).
- **In features:** call `track("event", props)` freely; it does nothing without consent.
- **Web Vitals (0138):** after consent, `src/lib/observability/web-vitals.ts` sends a `web_vital` event per CLS, LCP and INP measurement (`metric`, `value`, `rating`, `navigation_type`, `path`). Watch the production CLS rule with a trend insight on `web_vital` filtered to `metric = CLS`, aggregated as the 75th percentile of `value`, broken down by `path`: it should stay at or below 0.01 (and LCP under 2,500 ms, INP under 200 ms). Values cover a whole document visit, client-side navigations included.

## Feature flags

- **Evaluated on the server** in a loader (`src/functions/feature-flags.ts`) and SSR'd through the Query cache, so the server and browser render the same thing and the browser makes no flag request.
- **Never slow (0154):** with `POSTHOG_SECRET_KEY` (a Project Secret or Personal API key) flags are evaluated in memory from definitions polled every 30 s. Without it a flag request gives up after 300 ms (the flag is off) and answers are cached for 30 s per flag and visitor.
- **Unknown or unconfigured flags are off.** Before consent, flags are evaluated with a shared anonymous id and never record `$feature_flag_called`.
- **Example:** create a boolean flag `home-items-cta` in PostHog to show a call to action on the home page.

## Health

- **`GET /api/health`** (and `HEAD`) is for uptime monitors (0124): `200` with `{ status, checks: { database: { status, latencyMs } }, checkedAt }`, or `503` when the database doesn't answer within 3 s. Never cached, no failure details (they're in the log line).
- **`/health`** shows the same check as a page for people (noindex).
